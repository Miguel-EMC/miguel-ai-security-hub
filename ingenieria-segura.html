Un laboratorio que conecte todo

Construye un asistente documental para tres organizaciones ficticias: FastAPI autentica, una política determina recursos autorizados, OpenSearch recupera contexto permitido y LangGraph coordina pasos. El gateway valida cada herramienta; la capa de evaluación observa resultados y efectos. Usa datos sintéticos y un proveedor simulado antes de gastar en modelos reales.

Identidad y datos

Usuario, tenant, rol y clasificación acompañan cada solicitud. La identidad no se obtiene del prompt.

Decisiones y ejecución

El modelo propone; código y políticas autorizan. Un contenido recuperado nunca concede capacidades.

Evidencia y operación

Tests, evaluaciones, trazas y playbooks muestran qué control actúa y qué riesgo queda.

Secuencia: primero una tool y flujo fijo; después orquestación; luego retrieval multiusuario; finalmente AWS y campañas más amplias. No necesitas implementar toda la arquitectura en la primera semana.

Competencias y entregables

La secuencia de meses es orientativa. Los primeros cuatro bloques se trabajan en paralelo con el plan inicial de cuatro semanas. Una tarea está completa cuando hay una evidencia verificable, no cuando se termina un curso.

01 / Mes 1

Diseño y programación

Objetivo: Construir un sistema pequeño cuyo comportamiento puedas explicar y probar.

  • Separar transporte HTTP, casos de uso, políticas, repositorios y adapters de LLM/tools. No crear una clase por cada función: abstraer límites que realmente cambian.
  • Usar tipos, schemas de entrada/salida, errores de dominio y configuración explícita. El modelo produce datos no confiables, incluso si usa structured outputs.
  • Aprender composición y dependency injection, adapter para proveedores y strategy para políticas de recuperación. Aplicar SOLID donde reduzca acoplamiento; no como una lista ceremonial.
  • Documentar alternativas y consecuencias con ADR; revisar complejidad, dependencias y manejo de errores en PRs pequeños.

Laboratorio: Implementar un servicio FastAPI con un proveedor simulado y otro real intercambiables; un cambio de proveedor no modifica las reglas de permisos.

Criterio de avance: Entrega: estructura de módulos, dos ADR, esquema de errores, formatter/lint y tests de reglas de dominio. Explica qué separación facilita probar y cuál sería innecesaria.

02 / Mes 1–2

Patrones de agentes y estado

Objetivo: Elegir el patrón mínimo que resuelve la tarea.

  • Comparar chaining, routing, parallelization, orchestrator-worker y evaluator-optimizer. Un workflow tiene rutas definidas; un agente puede decidir pasos dentro de límites.
  • Orchestrator-worker: el coordinador divide trabajo, asigna workers y agrega resultados. Definir contratos, estado compartido, fallos parciales y límites de concurrencia.
  • Estudiar tool calling, supervisor y handoffs. No transferir más identidad, datos o permisos de los necesarios entre agentes.
  • Añadir persistencia, separación de sesiones, límite de pasos, cancelación y aprobación humana. Reanudar un checkpoint no debe repetir una acción irreversible.

Laboratorio: Resolver la misma tarea con flujo fijo y orquestador; comparar precisión, costo, latencia y superficie de ataque. El evaluator-optimizer no sustituye la evaluación independiente.

Criterio de avance: Entrega: diagramas, estado tipado, reglas de terminación y pruebas de worker fallido, bucle y reanudación.

03 / Mes 1–3

Testing, contratos y resiliencia

Objetivo: Comprobar invariantes deterministas antes de medir respuestas generativas.

  • Unitarios: políticas y lógica pura. Integración: API, base de datos, OpenSearch y herramientas. End-to-end: flujo real con componentes mínimos y datos sintéticos.
  • Tests de contrato: schema del proveedor, argumentos de tools y formato de respuesta. Fixtures aisladas y mocks solo en fronteras externas.
  • Pruebas negativas: usuario sin permisos, ID ajeno, timeout, proveedor 429/5xx, JSON inválido, error del índice y herramienta caída.
  • Async: distinguir I/O y CPU, llamadas bloqueantes, límites de concurrencia, cancelación y deadlines. Reintentar solo fallos transitorios; proteger efectos con idempotencia.
  • Usar pytest y HTTPX; parametrizar casos. Hypothesis como apoyo para generar entradas de políticas/schemas. Cobertura ayuda a localizar huecos, no prueba corrección.

Laboratorio: Simular una caída de recuperación y un timeout del modelo; comprobar respuesta controlada, trazas sin secretos y ausencia de acciones duplicadas.

Criterio de avance: Entrega: matriz de tests y fallos, ejecución repetible, reglas de retry y demostración de cancelación.

04 / Mes 2

Threat modeling y políticas

Objetivo: Convertir riesgos en controles y pruebas verificables.

  • Inventariar datos, herramientas, credenciales, modelos, memoria e índices. Dibujar límites de confianza y flujos de datos.
  • Usar STRIDE como apoyo y OWASP LLM/Agentic como catálogo. Seleccionar amenazas según el sistema, no marcar una lista sin analizarla.
  • Definir actor, precondición, activo, acción prohibida, impacto y control; asignar dueño y evidencia.
  • Distinguir confidencialidad (quién ve), integridad (quién cambia) y disponibilidad (quién consume). Agregar privacidad, límites de finalidad y retención.

Laboratorio: Modelar una orden maliciosa dentro de un documento recuperado que intenta usar una tool de exportación.

Criterio de avance: Entrega: threat model versionado, diez amenazas priorizadas, políticas de acceso y riesgo residual explícito.

05 / Mes 2–4

Autorización de herramientas y MCP

Objetivo: Asegurar que decidir una acción no equivale a estar autorizado para ejecutarla.

  • Derivar identidad y tenant del contexto autenticado, nunca de argumentos que el LLM elige. Verificar permiso por recurso y acción en cada llamada.
  • JWT es un formato: validar firma, issuer, audience, expiración y scopes según el flujo. Diseñar RBAC y condiciones por atributos/recurso cuando sean necesarias.
  • Construir un gateway de tools con schemas, allowlists, límites y auditoría; denegar por defecto. Separar credenciales por capacidad.
  • En MCP revisar origen del servidor, tools anunciadas, cambios en descripciones, token audience y scopes; el protocolo no elimina el riesgo de tool poisoning.
  • Aprobación humana ligada a acción y argumentos exactos, con expiración. Un cambio de parámetros debe invalidarla; evitar aprobación genérica para toda la sesión.

Laboratorio: Un usuario de tenant A pide una exportación de B: el gateway la rechaza aunque el modelo la solicite. Repetir con identidad manipulada y replay de aprobación.

Criterio de avance: Entrega: contrato de tool, matriz de permisos y pruebas de IDOR, escalación de privilegios y aprobación.

06 / Mes 3–4

RAG y OpenSearch seguro

Objetivo: Excluir información no autorizada antes de entregarla al modelo.

  • Aprender índices, mappings, analizadores, BM25, vectores, búsqueda híbrida y reranking; fijar dimensión y versión del modelo de embeddings.
  • Diseñar ingestión con procedencia, clasificación, tenant, ACL y versión. Los metadatos de permisos provienen de fuentes confiables.
  • Evaluar RBAC, permisos de índice, document-level security (DLS) y field-level security (FLS). DLS/FLS requieren configuración compatible y verificación con la versión usada.
  • No confundir tenants de Dashboards con aislamiento documental. Un filtro que el cliente puede omitir no es una frontera de seguridad.
  • Probar aislamiento en búsqueda lexical/vectorial/híbrida, get/mget, sugerencias y agregaciones si se habilitan. Revisar compatibilidad entre DLS, FLS y campos usados por políticas.
  • Incluir ACL en caché y memoria; invalidar al revocar permisos. Comprobar borrado en documentos, chunks, caché e índices de respaldo según la política. OpenSearch administrado, Serverless y local no ofrecen controles idénticos.

Laboratorio: Crear tres tenants con documentos públicos, internos y restringidos. Ejecutar consultas equivalentes por cada identidad y revocar un permiso durante una sesión.

Criterio de avance: Entrega: mappings y roles, matriz de acceso y evidencia de que los chunks de otro tenant nunca llegan al contexto. Comparar calidad de retrieval autorizado.

07 / Mes 3–5

Confidencialidad y ciclo de datos

Objetivo: Proteger datos en entrada, contexto, salida, logs, memoria y proveedores.

  • Clasificar datos y definir finalidad, retención y destinos permitidos; minimizar qué se envía a embeddings y modelos.
  • Detectar PII con Presidio o guardrails como una capa adicional. Medir falsos negativos en español y entidades del contexto ecuatoriano; un detector no garantiza anonimización.
  • Redactar logs y trazas; guardar IDs técnicos y decisiones en lugar de contenido completo cuando sea posible. Proteger los propios datasets de evaluación.
  • Cifrar tránsito y almacenamiento, gestionar secretos y rotación. Cifrado no impide acceso de una identidad autorizada incorrectamente.
  • Tratar embeddings como datos derivados potencialmente sensibles. Hashing o masking no convierten automáticamente datos en anónimos; evaluar reidentificación y correlación.
  • Definir borrado, revocación y exportación; estudiar backups y memorias persistentes. Revisar condiciones del proveedor para retención y uso de datos.

Laboratorio: Usar datos totalmente sintéticos con marcadores secretos únicos por tenant. Inspeccionar respuestas, logs, trazas, caché y memoria.

Criterio de avance: Entrega: inventario de datos, política de retención, pruebas de fuga y reporte de precisión/recall del detector.

08 / Mes 4–6

Guardrails y red teaming

Objetivo: Medir controles en el sistema completo, no solo resistencia del prompt.

  • Separar filtros de contenido, detectores de inyección, validación de outputs y autorización determinista. Los guardrails no sustituyen permisos.
  • Probar instrucciones maliciosas directas e indirectas en documentos, resultados de tools y memoria; observar tool calls y efectos reales además del texto.
  • Evaluar aislamiento de ejecución, egress allowlist, tamaño de entrada, límites de tokens/pasos y permisos del runtime.
  • Comenzar con Promptfoo sobre el endpoint del laboratorio. Añadir PyRIT para campañas de varios turnos; garak para sondeos de modelos/endpoints cuando responda a una pregunta concreta.
  • Aplicar Bedrock Guardrails en entradas/salidas según el flujo y documentar qué contenido inspecciona cada configuración. Detectar PII o grounding no prueba confidencialidad ni verdad universal.

Laboratorio: Comparar baseline y defensa sobre el mismo conjunto benigno/adversarial; variar herramienta, documento y memoria sin usar datos reales.

Criterio de avance: Entrega: campaña reproducible, traces relevantes, incidentes encontrados y mitigaciones. Practicar solo en entornos propios/autorizados.

09 / Mes 1–6

Frameworks de evaluación y medición

Objetivo: Separar calidad, seguridad, confiabilidad y costo en vez de producir una nota única.

  • Versionar dataset, prompts, modelo, embeddings, configuración del índice, tools y evaluadores. Registrar fecha y parámetros de cada ejecución.
  • Ragas para evaluar recuperación y generación; Promptfoo para escenarios y assertions. Elegir un framework inicial y conservar tests deterministas para políticas.
  • Separar dev/tuning y holdout. Curar casos con contexto, referencia/rúbrica, identidad, permiso esperado y acción prohibida.
  • Calibrar jueces LLM con revisión humana y casos de desacuerdo; registrar modelo juez y sesgos. La evaluación automática no sustituye verificación de hechos o permisos.
  • Repetir ejecuciones generativas para observar variabilidad; documentar denominadores, condiciones y límites. Cero fallos observados no garantiza cero riesgo.
  • Definir umbrales según impacto y baseline; bloqueo de permisos por tests deterministas, revisión de calidad y presupuesto de latencia/costo por separado.

Laboratorio: Comparar dos prompts y dos variantes de recuperación sin cambiar todas las variables a la vez; preservar un conjunto no usado para ajustar.

Criterio de avance: Entrega: reporte reproducible con resultados por categoría, ejemplos de fallos, costos y decisión de promoción/rechazo.

10 / Mes 5–8

LLMOps, AWS y respuesta a incidentes

Objetivo: Operar el sistema con controles observables y cambios reversibles.

  • Trazas por solicitud: identidad técnica, pasos, duración, política, tool y resultado; redactar contenido sensible. Usar OpenTelemetry o una plataforma como Langfuse tras evaluar acceso y retención.
  • Versionar artefactos y separar ambientes; CI ejecuta lint, tests y evaluación seleccionada. No enviar datasets sensibles a proveedores sin control.
  • IAM por capacidad, secretos, redes y KMS según arquitectura. Elegir Lambda/ECS por tiempo, carga, conexiones y ejecución; limitar costos y concurrencia.
  • Explorar AgentCore después de dominar el flujo local: investigar runtime, identidad y observabilidad disponibles en la región/versiones usadas.
  • Definir kill switch, rollback, revocación y playbook de fuga/acción indebida. La alerta debe incluir una acción y un dueño.

Laboratorio: Introducir una regresión de permisos y una fuga sintética; bloquear promoción y practicar revocación, rollback y reporte.

Criterio de avance: Entrega: pipeline, dashboard, presupuesto y simulacro documentado sin datos personales.

11 / Mes 7–10

Secure Tool Gateway y campañas

Objetivo: Consolidar arquitectura, retrieval y evaluación en un proyecto demostrable.

  • Integrar el gateway, OpenSearch y trazas con un API estable. Añadir al menos una operación con aprobación y efecto reversible en sandbox.
  • Ampliar ataques a variaciones multilingües y multi-turno; medir transferencias de datos entre agentes y contaminación de memoria.
  • Aplicar property-based tests a decisiones de autorización y fuzzing de schemas. No permitir que un juez LLM decida si se concede un permiso.
  • Documentar hallazgos con reproducción, impacto, causa raíz, corrección y regresión. Priorizar por impacto real, no por número de herramientas usadas.

Laboratorio: Ejecutar un benchmark interno sobre tres versiones y demostrar qué defensa cambia el resultado.

Criterio de avance: Entrega: repositorio ejecutable con configuración de ejemplo, campaña versionada y revisión de riesgos pendientes.

12 / Mes 11–12

Portafolio y criterio profesional

Objetivo: Mostrar evidencia de ingeniería de seguridad para agentes.

  • Publicar casos sintéticos: threat model, arquitectura, prueba, defensa, métrica y limitación. Separar trabajo propio de experiencia profesional.
  • Preparar relatos de decisiones: por qué un flujo fijo, por qué DLS/FLS, por qué un umbral y qué trade-off aceptaste.
  • Leer/reproducir un experimento de seguridad de modelos como exploración secundaria; matemáticas apoya la comprensión sin desplazar la práctica prioritaria.
  • Revisar cada trimestre prioridades según hallazgos y tiempo disponible. Avanzar por dominio demostrado, no por terminar videos.

Laboratorio: Demostrar en 15 minutos un ataque bloqueado, una regresión detectada y una decisión arquitectónica defendible.

Criterio de avance: Entrega: tres estudios de caso y un mapa de competencias con enlaces a evidencias, sin atribuirte experiencia no demostrada.

Cómo evaluar seguridad y confidencialidad

Reporta cada dimensión por separado. Un score alto de calidad no compensa una fuga; un scanner limpio no demuestra ausencia de vulnerabilidades.

DimensiónMediciónInterpretación
AutorizaciónAcciones ejecutadas sin permiso / intentos sin permisoObservar backend y efectos; no confiar en el texto del modelo.
ConfidencialidadCasos con fuga confirmada / casos adversariales de fugaSeparar salida, logs, memoria y contexto. Usar secretos sintéticos.
Retrieval autorizadoChunks no autorizados entregados al modelo / chunks recuperadosExigir cero en los tests definidos; no extrapolar a todos los ataques.
ASRAtaques que cumplen objetivo / ataques ejecutadosDefinir objetivo por caso; separar intento de ejecución de éxito.
Falsos bloqueosSolicitudes benignas bloqueadas / solicitudes benignasNo mejorar ASR rechazando todo.
Calidad RAGRecall/precision de retrieval y fidelidad al contextoMedir sobre referencias revisadas; respuesta sustentada puede usar una fuente falsa.
PrivacidadPrecision y recall de detección por tipo de PIIValidar idioma y dominio; revisar falsos negativos.
OperaciónLatencia p50/p95, costo por tarea y fallosRegistrar carga y límites; comparar bajo condiciones equivalentes.

Protocolo: define objetivo y política → prepara casos → fija versiones → ejecuta baseline → aplica un control → repite → revisa fallos → conserva holdout → documenta límites. Registra tamaño de muestra y repeticiones; considera intervalos de incertidumbre al comparar tasas. No declares el sistema seguro por obtener cero fallos en una muestra pequeña.

Fija versiones y consulta documentación antes de integrar. Algunas herramientas envían prompts, datasets o resultados a servicios externos: revisa la configuración y evita datos privados. Verifica licencias y costos para el uso previsto.

Con 8–10 horas semanales, reserva 4 h para laboratorio, 2 h para tests/evals, 2 h para conceptos y revisión, y 1–2 h para documentación. Si una competencia necesita más tiempo, mueve fechas; conserva la evidencia exigida.

Checklist de revisión de cada PR: amenaza o requisito claro, frontera de confianza, permisos, datos expuestos, fallo esperado, prueba relevante, trazas redactadas, versión de evaluación y rollback. Mantén una lista de pendientes y una decisión de riesgo aceptado cuando una protección no esté implementada.
