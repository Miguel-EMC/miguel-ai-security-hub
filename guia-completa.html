02
AWS Security Core
Mes 2

IAM y arquitectura segura como fundamento

Aprende a diseñar el sistema para que un LLM comprometido no equivalga a una cuenta AWS comprometida.

  • IAM users/roles/policies, trust policies, STS y resource policies.
  • Least privilege, separation of duties, KMS, Secrets Manager y CloudTrail.
  • API Gateway, Lambda permissions, S3 policies, VPC y security groups.
Recursos para este mes
  • Curso gratis AWS · Security Learning PlanSelecciona IAM e identidad; evita repetir la introducción general a cloud.
  • Documentación IAM · Evaluación de políticasAprende qué permite o deniega una solicitud.
  • Práctica IAM · Policy SimulatorComprueba tus roles con acciones y recursos concretos.
03
LLM Security
Mes 3

Riesgos específicos de aplicaciones LLM

  • Prompt injection directa e indirecta.
  • Sensitive information disclosure.
  • Improper output handling y excessive agency.
  • Supply chain, data/model poisoning y unbounded consumption.
Recursos para este mes
  • Guía OWASP · Top 10 LLM/GenAI 2026Revisa escenarios y mitigaciones; prioriza prompt injection y fuga de datos.
  • Curso + labs PortSwigger · Web LLM attacksHaz los labs de explotación de APIs de un agente.
  • Marco MITRE ATLASClasifica las técnicas que logres reproducir.
04
Agent Security
Mes 4

Herramientas, memoria, RAG y agencia

Pasa de “proteger el prompt” a proteger las capacidades reales del agente.

  • Tool misuse / tool abuse.
  • Indirect prompt injection desde documentos.
  • RAG poisoning, memory poisoning y context manipulation.
  • Excessive permissions, delegation y confused deputy.
Recursos para este mes
  • Guía OWASP · Top 10 Agentic ApplicationsRelaciona amenazas con memoria, delegación, herramientas y permisos.
  • Lab PortSwigger · Indirect prompt injectionReplica el patrón en tus documentos de prueba.
  • Guía AWS Seguridad para sistemas agenticObserva cómo se combinan capas de aplicación, identidad e infraestructura.

Los 3 proyectos que deben verte crecer

1. Agent Security LabMes 1–4

Agente deliberadamente vulnerable con datos public/internal/secret, RAG, tools y ataques controlados.

Demuestra: prompt injection, RAG poisoning, data leakage, authz y mitigaciones.

2. Secure Tool GatewayMes 5–8

Capa externa al LLM que decide si una tool call puede ejecutarse según identidad, recurso, acción y contexto.

Demuestra: secure-by-design, least privilege, IAM y policy enforcement.

3. AgentBreakMes 7–12

Runner para lanzar ataques reproducibles contra agentes y medir seguridad/robustez.

Demuestra: red teaming, evals, métricas, investigación y reporting.

Tu objetivo del primer mes no es “aprender ciberseguridad”. Es terminar con un sistema real que puedas enseñar y decir: “esta vulnerabilidad existía, la reproduje, diseñé esta defensa y medí el resultado”.

Métricas que aprenderás a usar

MétricaQué pregunta responde
Attack Success Rate (ASR)¿Qué porcentaje de ataques consigue el objetivo adversarial definido?
Sensitive Data Leakage Rate¿Con qué frecuencia aparece información que la política prohíbe revelar?
Tool Policy Violation Rate¿Cuántas acciones intentan o consiguen salir de los permisos previstos?
False Refusal Rate¿La defensa bloquea demasiadas solicitudes legítimas?
Detection Rate¿Cuántos ataques o comportamientos anómalos detecta el sistema?
Mean Time to Reproduce¿Qué tan rápido puedes convertir un fallo extraño en un caso determinista?

Lo que NO priorizarás este año

  • Frontend avanzado por obligación.
  • Otro framework backend solo para ampliar la lista.
  • Data Engineering profundo salvo necesidad del proyecto.
  • Certificaciones sin laboratorio o evidencia.
  • Aprender 10 frameworks de agentes a la vez.
  • Seguridad ofensiva contra sistemas no autorizados.

Señales de que el roadmap funciona

  • Puedes explicar por qué un ataque funcionó, no solo copiarlo.
  • Tus defensas viven fuera del prompt cuando corresponde.
  • Tus IAM policies son mínimas y justificables.
  • Tus ataques son reproducibles y medibles.
  • Produces threat models y diagramas claros.
  • Lees papers y puedes reproducir al menos parte del método.

Regla de reposicionamiento profesional

No cambies todavía tu título a AI Security Engineer solo por estudiar. Hazlo cuando puedas demostrar al menos:

1. Un agente vulnerable + mitigado.
2. Una arquitectura AWS segura y documentada.
3. Un benchmark/red-team runner reproducible.

Hasta entonces, tu posición natural sigue siendo AI Engineer / AI Systems con una especialización creciente en seguridad.
